# CS5481 项目数据接口

版本：`v2.1`
状态：M1–M3 数据契约已定义；M4–M6 待对应成员补充

本文档定义各阶段之间的数据交接格式。实现代码可以各自独立，下游只依赖这里已经
确认的文件契约，不读取上游的内部变量或临时数据库。

## 1. 分工与状态

| 阶段 | 负责人 | 当前状态 | 主要输入 | 主要输出 |
| --- | --- | --- | --- | --- |
| M1 数据采集 | M1 | 已定义 | Guardian API | Raw JSONL、Documents JSONL |
| M2 Chunking | M2 | 已实现 | M1 Documents | 三种 `news_chunks.v1` JSONL 与 manifests |
| M3 Embedding | M3 | 已实现 | `news_chunks.v1` JSONL | Chroma 持久化向量集合、索引 manifest |
| M4 Retrieval | M4 | 待补充 | M3 向量库 | 待 M4 定义 |
| M5 Generation | M5 | 待补充 | M4 检索结果 | 待 M5 定义 |
| M6 Evaluation | M6 | 待补充 | QA 集及生成结果 | 待 M6 定义 |

## 2. 通用约定

- JSONL 使用 UTF-8，每行一个 JSON 对象。
- 每条记录必须包含稳定主键和 `schema_version`。
- 引用必须保留原文 URL、标题和发布时间。
- 文件格式不兼容变更时升级 `schema_version`，并更新本文档。
- 交付数据时同时提供 manifest，记录数量、参数和 SHA-256。

## 5. M2：Chunking

### 5.1 输入与输出

输入为 M1 标准文档：`data/documents/documents.jsonl`。M2 生成三种可对照的 chunk 文件：

| 文件 | 策略 | 默认参数 |
| --- | --- | --- |
| `data/chunks/chunks_A.jsonl` | 固定长度窗口，带重叠；尽量在句子边界结束 | `chunk_chars=1200`, `overlap_chars=150` |
| `data/chunks/chunks_B.jsonl` | 段落优先组合；超长段落按句子拆分，必要时按字符拆分 | `chunk_chars=1200` |
| `data/chunks/chunks_C.jsonl` | 句子优先组合，每块前缀附文章标题；超长句按字符拆分 | `chunk_chars=1200` |

生成命令：`python -m scripts.m2_chunking.chunk_documents`。可通过 `--chunk-chars` 和 `--overlap-chars` 修改参数。输入、参数和脚本版本相同即可复现 chunk 内容。

### 5.2 Chunk schema

三种输出均为 UTF-8 JSONL，schema 版本为 `news_chunks.v1`，每行包含：

| 字段 | 类型 | 定义 |
| --- | --- | --- |
| `schema_version` | string | 固定为 `news_chunks.v1` |
| `chunk_id` | string | 对 `document_id`、策略名、块序号和 chunk 文本计算的 SHA-256；输入不变时稳定 |
| `document_id` | string | 对应 M1 文档主键 |
| `chunk_index` | integer | 文档内从 0 开始的块序号 |
| `strategy` | string | `fixed_overlap`、`paragraph` 或 `sentence_title` |
| `text` | string | M3 用于生成 embedding 的文本 |
| `word_count` | integer | `text.split()` 的词数 |
| `citation` | object | 原文定位信息，见下表 |
| `metadata` | object | 可用的栏目和语言字段 |

`citation` 包含 `url`、`title`、`published_at_utc`、`source_name`、`source_domain`，其值来自对应 M1 文档。

### 5.3 Manifest

每个输出文件有配套 manifest：`chunks_A.manifest.json`、`chunks_B.manifest.json`、`chunks_C.manifest.json`，位于 `data/chunks/`。Manifest 记录 `schema_version=chunks.manifest.v1`、策略、生成时间、输入路径及 SHA-256、输出路径及 SHA-256、参数、文档数、chunk 数及词数统计。

### 5.4 下游约定

M3 以 `text` 作为 embedding 输入。在当前 Chroma 实现中，`chunk_id` 保存为记录 ID，`text` 保存为 document；`schema_version`、`document_id`、`chunk_index` 和 `strategy` 保存为标量 metadata。`citation` 的字段展开为 `citation_url`、`citation_title`、`citation_published_at_utc`、`citation_source_name` 和 `citation_source_domain`；可用的栏目、语言等标量 `metadata` 字段加上 `document_` 前缀保存。`word_count` 未写入 Chroma metadata，需要时可从文本计算或回查 chunk JSONL。这样 M4/M5 可直接取得 chunk 标识、文本和引用信息，无需查询 M1 私有数据库。完整字段映射见 [M3 → M4 对接文档](../m3/M4_HANDOFF.md)。

本次 3,152 篇文档生成 A/B/C 分别为 17,015、15,914、16,432 个 chunks。三者的优劣和统计见 `scripts/m2_chunking/README.md`。这些规模统计不是检索质量结论。

## 6. M3：Embedding 与向量库

实现：`scripts/m3_embedding/index_chunks.py`。M3 接收 M2 `news_chunks.v1` chunk 文件；默认分别为 A、B、C 三种策略建库。

- **Embedding backend**：Sentence Transformers，本地运行 `sentence-transformers/all-MiniLM-L6-v2`；可通过 `--model` 指定其他兼容模型。向量使用 L2 归一化。
- **向量库**：ChromaDB `PersistentClient`，持久化路径 `data/vector_store/chroma/`；相似度空间为 cosine。
- **集合命名**：`chunks_{strategy}_{chunk_sha前10位}_{model_fingerprint前10位}`。输入文件或模型 revision 变化会产生新集合，不覆盖旧版本。
- **Metadata**：`document_id`、`chunk_index`、`strategy`、chunk schema、原文 URL/标题/发布时间/来源，以及可用的栏目和语言字段；正文保存在 Chroma document 字段。
- **缓存**：`data/vector_store/embedding_cache.sqlite3` 以模型 revision 与 chunk 文本哈希为键，避免重跑重复计算相同向量。
- **Manifest**：`data/vector_store/manifests/{collection}.manifest.json` 记录输入哈希、模型/修订号/维度、距离度量、集合名、批次大小和缓存命中统计。

运行：

```bash
python -m pip install -r requirements.txt
python -m scripts.m3_embedding.index_chunks --strategies A,B,C --batch-size 64
```

首次运行需要下载模型文件；也可使用已缓存模型或 `--model /path/to/local/model` 离线运行。默认自动选择设备；可用 `--device cpu`、`--device mps` 或 `--device cuda` 指定。M4 可调用 `SentenceEmbeddingModel.encode_query()` 编码问题，并用 `load_collection(collection_name)` 加载已构建集合。查询检索逻辑属于 M4，不包含在本模块。

索引输入发生变化时将创建新版本集合；同一输入和模型再次运行会复用向量缓存，并通过稳定 chunk ID upsert。不要在集合名或 manifest 中复用不同输入或不同模型版本。

M3 的完整数据字段、API 示例和验证结果见 [M3 → M4 对接文档](../m3/M4_HANDOFF.md)。

## 5. M2: Chunking

M2 reads `data/documents/documents.jsonl` and writes:

- `data/chunks/chunks_A.jsonl`: fixed character windows, default 1,200 characters with 150-character overlap; sentence boundary preferred near the end of a window.
- `data/chunks/chunks_B.jsonl`: paragraph-first grouping up to 1,200 characters; oversized paragraphs are split at sentence boundaries, with character slicing as a final fallback.
- Each output has a corresponding `.manifest.json` with input/output SHA-256, parameters, document and chunk counts, and word-count statistics.

Run `python -m scripts.m2_chunking.chunk_documents` from the repository root. `--chunk-chars` and `--overlap-chars` set reproducible parameters (the overlap applies to strategy A only).

Chunk schema: `news_chunks.v1`. Each record contains `chunk_id` (SHA-256 of document ID, strategy, zero-based index, and text), `document_id`, `chunk_index`, `strategy`, `text`, `word_count`, `citation` (`url`, `title`, `published_at_utc`, `source_name`, `source_domain`), and available `section_id`, `section_name`, and `language` metadata. M3 consumes `text` for embedding, stores `chunk_id` as the Chroma record ID and `text` as the document, and flattens citation and available scalar document metadata into Chroma metadata so M4/M5 can cite the original article. `word_count` is not stored in Chroma metadata; see the [M3 to M4 handoff](../m3/M4_HANDOFF.md) for the exact field mapping.

### 5.1 Strategy comparison

On the supplied 3,152-document corpus, fixed-overlap (A) produced 17,015 chunks (mean 169.11 whitespace-delimited words), paragraph-first (B) produced 15,914 (159.13), and sentence-first with title prefix (C) produced 16,432 (166.94). A preserves some boundary context through overlap but duplicates text and can split natural units. B preserves paragraph groupings and has the fewest chunks in this run, but depends on paragraph structure in the input. C usually keeps sentences intact and repeats the title as context, with some additional token cost. These are structural trade-offs; retrieval superiority has not yet been established. M3/M4 should compare retrieval on the same queries, embedding model, and top-k, using Recall@k/Hit@k, latency, and citation relevance.
